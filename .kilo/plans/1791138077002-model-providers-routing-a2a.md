# Model Providers, Routing Metadata, and A2A Connectivity

## Goal

Expand first-party LLM provider coverage and account management; make model capability and routing metadata discoverable, sourced, and safe to use; add bidirectional Agent2Agent connectivity without bypassing PlayWeld's task, access, or approval boundaries.

## Confirmed Scope

- Keep unlimited, separate provider accounts. Add named integrations for OpenAI, Google Gemini, OpenRouter, xAI, Mistral, DeepSeek, Groq, and Azure OpenAI. Retain Anthropic and the generic OpenAI-compatible endpoint for local and compatible services.
- Provider credentials are API keys and custom headers stored in the existing encrypted credential store. OAuth, device login, and cloud-native identity flows are out of scope.
- Enrich provider endpoint metadata with a PlayWeld-maintained, source-linked catalog. Record source and freshness per field, preserve manual overrides, and leave unsupported facts unknown. Do not silently run billable completion probes.
- Automatically apply only high-confidence, deterministic role/work-type mappings backed by provider/catalog task-family facts and verified capabilities. These fields remain routing eligibility restrictions; do not infer incompatibility from absent evidence. Preserve manual overrides.
- Use A2A v1.0 in both directions. PlayWeld may call configured external agents, and local harnesses may submit/manage scoped tasks through PlayWeld. Inbound access is loopback-only; remote/LAN exposure is deferred.
- Inbound A2A clients can submit, inspect, continue, stream, and cancel tasks only within explicit Project/role grants. All work uses the existing scheduler, broker, access mode, and approval flow. No direct settings, credentials, or administrative RPC access.
- Outbound A2A uses configured static API-key, bearer/basic, or custom-header credentials. OAuth/OIDC is deferred. “ACP” is not a new platform protocol here: Agent Communication Protocol is being consolidated into A2A; Agent Client Protocol is a separate editor-to-agent interface and is out of scope.

## Repository Evidence

- Provider kinds are currently only `openai-compatible` and `anthropic` (`packages/contracts/src/models/schema.ts`); account records already support multiple accounts and encrypted API keys/headers (`packages/platform-service/src/models/model-registry.ts`).
- The provider registry is a static adapter map. Account RPC supports update, but the Models view currently lacks account editing; it supports add, test, discover, enable/disable, and remove (`packages/platform-service/src/models/providers/`, `packages/theia-control-room/src/browser/models-widget.tsx`).
- Missing capability booleans are currently defaulted to false (except chat=true), so unknown and unsupported are conflated. Model metadata has one whole-record source/timestamp; work types and roles are manually edited and are hard router filters (`packages/platform-service/src/models/model-registry.ts`, `packages/contracts/src/models/schema.ts`, `packages/platform-service/src/models/router.ts`).
- The platform service currently exposes only authenticated local IPC. A2A therefore needs a separate, explicitly enabled loopback listener rather than widening the service RPC listener (`packages/platform-service/src/service.ts`).
- The common chat message currently carries text only. Provider-advertised features must not be marked router-usable unless the normalized request contract can actually express them.

## Ordered Work

1. **Verify current provider and protocol contracts.** Write a dated research note using vendor primary sources for the named providers' authentication, model-list metadata, request/stream formats, tool/structured-output behavior, embeddings, and usage. Verify against the official [A2A v1.0 specification](https://a2a-protocol.org/v1.0.0/specification/). Keep claims provider-specific; identical OpenAI-compatible paths do not imply feature parity.
2. **Evolve contracts and persistence compatibly.** Extend provider-kind/account configuration schemas for the selected providers, including Azure endpoint/deployment/API-version fields. Add field-level model metadata value/source/fetched-at representation and an explicit unknown state for boolean capabilities. Migrate existing accounts without changing IDs or secrets; preserve manual metadata and existing routing behavior. Treat legacy provider-default false values as unverified, not vendor-declared unsupported. Ensure only `true` satisfies a required capability and unknown never broadens the eligible set.
3. **Implement and test provider adapters.** Add provider-specific endpoint/auth/request/response mappings for the selected roster, reusing transport code only where contracts match. Normalize model discovery, chat, streaming, tool calls, structured output, usage, embeddings, health/test results, and limits where each provider supports them. Keep unsupported operations explicit; do not claim or route a capability that the normalized PlayWeld request path cannot use. Catalog prices remain estimates, distinct from reported usage/cost.
4. **Complete account and catalog settings UX.** Add provider presets and provider-specific account fields; expose existing account-update support for name, endpoint, enabled state, and credential replacement/removal. Show per-account test/refresh status and sanitized diagnostics. Keep preview-and-select discovery. Display capability values as supported, unsupported, or unknown with source and freshness; support stale refresh and field-level manual overrides.
5. **Add catalog enrichment and automatic routing metadata.** Merge, in priority order, manual overrides, current account endpoint declarations, and versioned PlayWeld catalog facts sourced to provider-published material. Do not introduce a hosted metadata service. Apply deterministic mappings only for high-confidence provider/catalog categories and local role/work-type IDs; preserve user overrides and recalculate only generated fields when rules or local role taxonomy change. Empty or unrecognized assignments remain unrestricted. Keep outcome-learned quality ranking separate from hard eligibility tags.
6. **Add outbound A2A connections.** Store endpoint, discovered Agent Card/interfaces/skills, health, and encrypted static credentials as separate agent connections, not model-provider accounts or MCP tools. Discover and review advertised capabilities before use; offer remote delegation through the existing broker, record task/cost/audit identity, stream status/artifacts, and support polling/cancel/reconciliation. Existing access modes govern disclosure and side effects; external results never authorize tool calls or changes. Treat cards, messages, files, and artifacts as untrusted data; enforce HTTPS except explicitly configured loopback agents, bound payloads/downloads, constrain redirects, and never forward credentials across origins. Start with A2A JSON-RPC over HTTP(S) and streaming; clearly report unsupported bindings/auth schemes and do not silently downgrade.
7. **Add the inbound A2A task gateway.** Implement an opt-in A2A v1.0 Agent Card and task façade on a configured loopback-only address/port; listener conflicts fail closed and must never fall back to a wildcard bind. Issue revocable per-client bearer credentials with explicit Project and role/task grants. Map A2A task create/get/continue/stream/cancel to existing durable task lifecycle operations. Caller identity cannot raise access ceilings or skip approvals. Reject untrusted Host/Origin values, disable permissive CORS, bound request bodies/concurrency, and rate-limit clients. Do not expose local service RPC, model/provider credentials, settings, or project enumeration. Defer public/LAN listeners and webhook push notifications.
8. **Synchronize design and generated references.** Record confirmed requirements separately from engineering defaults; update the provider, metadata, and agent-connection architecture/decision entries and dependency-ordered development plan. Regenerate/check RPC and settings references as needed; add the required pending `docs/changes/` record and changelog coverage for implementation work.

## Validation and Acceptance

- Contract and migration tests cover old account/model records, manual-value preservation, unknown metadata, and redacted credential handling.
- Provider fixture tests cover each named adapter's discovery parsing, feature normalization, streaming/tool behavior where supported, usage, auth failures, rate limits, malformed responses, cancellation, and sanitized errors. Generic OpenAI-compatible and Anthropic regressions remain green. No paid live request is required for unit/contract acceptance.
- Routing tests prove only verified `true` capabilities satisfy requirements, high-confidence generated tags apply and refresh correctly, manual edits survive catalog refresh, absent evidence stays unrestricted, and empty pool intersections never widen selection.
- A2A fixture interoperability tests cover Agent Card discovery/interface selection, static auth, submit/continue/get/stream/cancel, artifacts, malformed or hostile remote content, task recovery, audit records, and errors without unsafe retries. Inbound integration tests prove loopback-only binding, client revocation and Project/role isolation, access-mode ceilings, Ask always approvals, and no administrative RPC exposure.
- UI tests cover account edit/credential replacement, account health, catalog refresh/provenance, unknown capability states, and generated-versus-manual routing metadata.
- Run focused contracts/platform-service/Theia tests, then repository build/typecheck/lint/test and formatting checks. Distinguish fixture-tested behavior from live provider/A2A interoperability; do not claim broad vendor or remote-agent acceptance without those live runs.

## Explicitly Out of Scope

Provider OAuth/cloud IAM; remote or LAN inbound A2A exposure; an invented ACP protocol; Agent Client Protocol integration; A2A gRPC, webhook push, or OAuth/OIDC in this first scope; direct inbound administration/tool RPC; silent model completion probes; a hosted model-catalog service; and multimodal chat payload expansion beyond the current normalized contract.
